## 一、你反馈的"误判"：根因找到了

**`126.37.15.22` 这条被标成机房，是因为代码拿 `proxy` 字段当了机房判据。**

`vpn_utils.py` 原来的判定逻辑是：

```python
ip_type = "residential"
if item.get("mobile"):
    ip_type = "mobile"
elif item.get("hosting") or item.get("proxy"):   # ← 这里
    ip_type = "hosting"
```

我实测了这条 IP 在各家接口的原始返回（ip-api）：

```json
{"isp": "SoftBank Corp.", "org": "SOFTBANK Corp", "as": "AS17676 SoftBank Corp.",
 "hosting": false, "proxy": true, "reverse": "softbank126037015022.bbtec.net"}
```

- `hosting: false` —— 官方自己都说不是机房；
- `proxy: true` —— 这只说明"这个 IP 是 VPN/代理出口"，**每个 VPNGate 节点都是 true**，因为你的节点本身就是 VPN 出口；
- 结果代码走了 `or item.get("proxy")` 分支 → 判成机房。

更麻烦的是 `hosting` 字段本身也不可信：我把当前 **98 个节点全部查了一遍，`hosting=true` 的只有 2 个**，连 DigitalOcean、SoftEther 自家服务器都标的是 false。也就是说旧逻辑实际是"用 proxy 标记把几乎所有家宽都标成机房"，而且方向刚好错反了。

### 新判定逻辑（`vpn_utils.py`）

按优先级：

1. **移动网络特征** → mobile（`mobile`/`cellular`/`wireless`/`lte`/`docomo, inc`…）
2. **云/机房/IDC 特征** → hosting（`digitalocean`/`softether`/`vpngate`/`hosted`/`hosting`/`datacenter`/`vps`…）
3. **消费级宽带 ISP 特征** → residential（`softbank`/`kddi`/`ocn`/`korea telecom`/`kornet`/`sk broadband`/`virgin media`/`rostelecom`/`fpt telecom`…共 100+ 关键词）
4. 关键词判不出来的（一般是小众运营商）→ 做一次 **PTR 反向域名反查**，识别 `*.bbtec.net`、`*.dynamic.*`、`*-pool-*`、`*.cable.*` 这类家宽/动态池特征
5. 都没结论 → 才退回 ip-api 标记，最后默认按家宽处理

`proxy` 字段**不再参与类型判定**，单独存成 `is_vpn_exit`，面板上显示为"VPN出口IP"。

**旧缓存会自动失效**：缓存条目里加了 `cls_ver`，版本不匹配就重查，不需要你手动删 `ip_cache.json`。

### 实测对比（同一批 98 个节点）

| 判定方法 | 住宅 | 机房 | 移动 |
|---|---|---|---|
| 旧逻辑（proxy 当机房） | 37 | **60** | 1 |
| 新逻辑 | **78** | 17 | 3 |

新的 17 个"机房"是：SoftEther 自家 14 台公共服务器（`public-vpn-*.vpngate.v4.open.ad.jp`，确实是 IDC）+ DigitalOcean + Hosted America + Play2go，判得对。
你的案例 `126.37.15.22` → `residential`，依据显示"机构关键词命中宽带运营商(softbank)"。

**面板现在会把判定依据显示出来**（卡片上的"判定依据"一行，节点表鼠标悬停 IP类型也有），误判你能一眼看出是哪个关键词命中的，好加词。

## 二、"稳定点"改了这些

### 1. `vpngate9_guard.py`（守护脚本，改动最大）

| 问题 | 修复 |
|---|---|
| **`idx` 先用后定义**：遇到第一个被禁用的通道直接 `UnboundLocalError` 崩掉，systemd 每 10 秒重启一次 → 守护完全失效 | 先取 `idx` 再判断。已用你的场景实测：旧版崩溃，新版正常 |
| **硬编码 `country=Japan&ip_type=residential`**：守护一介入就把通道的国家覆盖成日本，9 条通道慢慢全变日本 | 改用 `/api/status` 里每个通道自己的 `force_country` / `force_ip_type`。实测 CH3 用 `Korea Republic of` 重连 ✓ |
| 每轮都白拉一次全量节点（`if (do_rotate or True)` 恒真） | 删掉，不再需要 |
| 凭据硬编码 `admin/admin`，面板改密后守护静默失效 | 自动读 `vpngate_data/ui_auth.json`，读不到才回退默认值并警告（**本版已升级为守护令牌，见第三节**） |
| 网络抖动就换节点 | 连续 `FAIL_TOLERANCE`（默认 2）轮测不到流量才动手 |
| 反复重连 | 加 `RECONNECT_COOLDOWN`（默认 120 秒）冷却 |
| **和面板 watchdog 抢同一个 tun**：两条链路同时重连 | 默认 `HANDLE_DISCONNECTED=False` —— 掉线交给面板 watchdog，守护只管"假连接"和定时轮换，各管一段不打架 |

### 2. `vpngate9_multi.py`（主程序）

| 问题 | 修复 |
|---|---|
| **`do_POST` 完全没有鉴权**：公网任何人可调 connect/disconnect/toggle/fetch_nodes | 除 `/api/login` 外，写操作未登录一律 401（已实测） |
| `toggle` 接口没做索引越界检查，`/api/channel/99/toggle` 会 500 | 加边界判断，返回 400（已实测） |
| **隧道判活用 `ping -I tun 8.8.8.8`**：很多 VPNGate 节点丢 ICMP，隧道其实是通的却被判死 → 反复换节点、通道闪断 | 新增 `vpn_utils.probe_tunnel()`：先用**绑定 tun 的 TCP 连接**探测（必须绑定成功才采信，避免走物理网卡造成假活），失败再退回 ping |
| 一次判死就重连（5 次 ping 失败） | 改成连续 `FAIL_TOLERANCE`（默认 3）轮不通才重连，单次抖动只记日志 |
| watchdog 全程持锁，探测期间面板点"连接"最多卡 25 秒 | 探测在锁外做快照，面板不再被卡 |
| 每 10 秒 × 9 通道 × 5 次 ping ≈ 4.5 ping/秒的探测风暴 | 每轮每通道 1 次 TCP 探测，负载降到原来的 1/5 |
| 前端 `for(var i=0;i<6;i++)` 遗留：CH6~CH8 的下拉选择被 3 秒轮询冲掉 | 改为按实际通道数 |
| **面板没有通道开关控件**，`toggleChannel()` 引用的 `tog_*` 元素根本没渲染，README 说的"用面板开关关掉"做不到 | 卡片上补上"守护自动重连"勾选框 |
| `/api/nodes` 只回 200 条，节点池却是 300，会出现"看不见的节点被自动选中" | 统一为 300 |
| 日志写着 "6 proxies started" 等 6 通道遗留文案 | 改为动态数字 |

### 3. `vpn_utils.py`

- 新增 IP 类型判定器 + PTR 反查（见上文）
- 新增 `probe_tunnel()` 隧道判活
- 新增 `_apply_cache_entry()` 统一缓存回填

### 4. `proxy_server_multi.py`

- 绑定失败时的回退地址由 `0.0.0.0` 改为 `127.0.0.1`。原实现一旦走到这条分支，9 个无认证的 SOCKS5 端口会直接暴露到公网（默认配置走不到，但这是个安全雷）。

### 5. `install.sh`

- systemd 加 `StartLimitIntervalSec=0`（否则崩溃 5 次后 systemd 就放弃不再拉起）、`LimitNOFILE=65535`、`After/Wants=network-online.target`
- 部署后 `chmod 600 ui_auth.json`（原来 `chmod -R 755` 把密码文件变成全机可读）
- 部署时若发现旧版明文密码，**就地升级为 PBKDF2 哈希**再启动；同时 `chmod 600 guard_token`
- 修掉登录页模板缺 `${error_display}` 占位符导致"账号或密码错误"一直显示的毛病，并支持显示限速提示
- 新增 `ml passwd` 子命令（忘记面板密码时的救援入口）
- 部署完成的提示里加了"请立即修改默认账号密码"

## 三、新增：在面板里修改管理账号和密码

入口：登录后右上角 **管理员**（原来是"修改账号密码"，只能改密码，账号只能作为校验项）。

### 改了什么

| 项 | 现在 |
|---|---|
| **新账号** | 可留空（不改）；3~32 位，仅 `A-Za-z0-9_.-`，会校验与当前是否相同 |
| **新密码** | 可留空（此时只改账号，密码沿用）；**至少 8 位**（原来只要 4 位），不能与账号相同、不能全同字符、拒绝常见弱口令 |
| **确认新密码** | 前端 + 后端双重校验一致性 |
| **身份校验** | 必须提供当前账号 + 当前密码，失败计入限速 |
| **改完的会话** | `invalidate_all_sessions()` 清掉所有登录态，**强制重新登录**（旧 cookie 立刻 401） |
| **密码存储** | `ui_auth.json` 只存 `pbkdf2_sha256$200000$salt$hash`；旧版明文文件在首次启动时自动升级，升级后日志会提示 |
| **限速** | 登录**和**改凭据接口共用：同一 IP 连续 5 次失败锁定 5 分钟（429 / 跳 `/?error=locked`） |
| **接口** | 新 `POST /api/admin/credentials`（JSON）；旧 `POST /api/admin/change_password`（form）保留兼容 |
| **退出登录** | 新增 `POST /api/logout` + 弹窗里的"退出登录"按钮，清 cookie 并跳回登录页 |
| **演练/救援** | 忘密码时 `ml passwd <新密码>` / `ml passwd <新账号> <新密码>`，改完**立即生效，无需重启** |

### 守护脚本不会因为改密码失联（重点）

面板启动时会在 `vpngate_data/guard_token` 生成一个 64 位十六进制**长效令牌**（chmod 600），守护脚本优先用它认证：

- 该令牌**不属于会话**，`invalidate_all_sessions()` 清不到它 → 改账号密码、面板重登，守护照常跑
- 兜底顺序：`guard_token` → `ui_auth.json` 明文（仅旧部署）→ 环境变量 `VPNGATE_USER`/`VPNGATE_PASS`
- 令牌不对/文件缺失时，日志会打 `[warn] 面板返回 401...`，不再静默失效

> **升级提醒**：这次升级后请 `systemctl restart vpngate9-guard`。因为面板会把 `ui_auth.json` 里的明文升级成哈希，**旧版守护脚本读不到明文就会登录失败**；新版守护改用令牌文件后不依赖明文。

## 四、新增：9 条通道各用不同国家 / 不同出口 IP

你要的「CH0 日本、CH1 美国、CH2 越南……」这种配置**本来就支持**（每张卡片有独立的国家下拉），
但原实现有个致命问题：**9 条通道几乎一定会撞到同一个出口 IP**，等于白开几条通道。

### 为什么会撞（原代码的坑）

```python
used_ips = set(c.node_ip for c in channels if c.state == "connected" and c.node_ip)
pool = filtered[:min(30, len(filtered))]
return random.choice(pool)
```

1. **只统计 `connected`**：而建隧道最长要 45 秒。启动时是「连一条 → `sleep 2` → 连下一条」，
   前一条还在握手、状态是 `connecting`，`used_ips` 里根本没有它 → 后一条自由挑，撞车概率极高。
2. **候选池被砍到 30 个**：按速度排序后只在前 30 个里随机，日本 40 多个节点也只用到前 30 个。
3. **排除后为空时直接回退到"不排除"**：也就是"找不到没被占的，就允许重复"，还完全静默。

### 现在的做法

- 新增 **出口 IP 预占**：选中节点的**那一刻**就把 IP 记到该通道的 `reserved_ip` 上，
  其它通道选节点时会避开它（不管它是否已经连通）。连接成功 / 失败 / 断开都会正确释放。
- 选节点的「读占用表 + 预占」用一把锁包住，**并发**点连接、watchdog 重连、守护脚本重连都不会抢同一个 IP。
- 候选池改为**该国全部节点**，只在「未占用」的里面挑（再取最快的前 12 个随机，兼顾质量与分散）。
- 三级回退：同国家+IP类型 → 同国家（放宽类型） → 才允许复用（并打日志、在卡片上标 **IP复用**）。
- 卡片顶部显示 **出口 N/9**；两条通道撞同一 IP 会标红 **IP重复**（后端在 `/api/status` 里算好 `ip_dup_with`）。
- 国家下拉现在带**剩余可用节点数**（如 `Japan · 剩 39/42`），选之前就知道够不够。
- **断开按钮不再清空国家设置**（原来会在断开时把 `force_country` 抹掉，固定出口要重选一次）。

### 一键分配（面板右上角「分配出口」）

| 方式 | 行为 |
|------|------|
| 尽量分到不同国家/地区 | 按各国在线节点数从多到少，一条通道一个国家；国家不够时在节点多的国家上多开（IP 仍不重复） |
| **全部通道用同一个国家/地区** | 你指定一个国家，9 条通道全从该国取节点，**只要该国可用 IP ≥ 通道数，9 个出口 IP 互不相同** |
| 不限国家，只保证出口 IP 互不重复 | 只管 IP，不管国家 |

先出**预览**（含每条的通道/国家/出口 IP/运营主体/该国节点数 + 风险提示），确认后才下发；
下发时前端把预览过的 `node_id` 一起回传，**预览 = 实际应用**（后端算法本身也是确定性的）。

「同一个国家」这个模式的几个细节：

- 国家下拉按**可用节点数降序**排（`Japan · 可用 42/42`），默认就选中可用最多的那个；右侧实时提示
  “可用 N 个，本次需要 M 条”，够是绿的、不够是橙的。
- 该国可用 IP **不够**时不硬凑：只分配够用的条数，未分到的通道保持原样，预览里用红框写明还差几条，
  并列出哪些国家的可用节点数够填满。勾上「用其它国家/地区补满剩余通道」才会拿别的国家补齐（IP 仍不重复）。
- 轮询刷新不会冲掉你已选的国家（重建下拉时保留当前值）。
- 你**显式点名**一个默认被排除的国家（如 China）时会被尊重并给出说明，而不是静默忽略。
- 掉线重连也遵循这套规则：watchdog 用该通道自己的 `force_country` 找同国家的**未占用** IP，所以
  「9 条通道全日本 + IP 各不同」在长期运行中能自我维持。

自动分配默认**跳过中国节点** —— VPNGate 的 CN 节点基本是境内家宽，当境外出口没意义且通常只有 1 个。
手动指定仍然可以，想改这个行为用 `VPNGATE_EXCLUDE_COUNTRIES=china,xxx`（留空=不排除）。

### 必须说清楚的现实约束

**"9 个通道 = 9 个不同国家"这件事，VPNGate 撑不住。** 我实测了当前接口：

```
总节点 98 个，覆盖 10 个国家/地区：
  Japan 42 | Korea 33 | Thailand 8 | United States 5 | Russian Federation 3
  Viet Nam 2 | United Kingdom 2 | China 1 | Myanmar 1 | Peru 1
```

只有 4 个国家的节点数 ≥ 5，一半国家只有 1~2 个节点，**掉线就无备选**。
所以当天能不能凑满 9 个不同国家要看运气；面板会在预览里如实告诉你差多少、哪几个国家是"独苗"。

真正稳定能做到、也是这个功能硬保证的是：**9 条通道 = 9 个互不相同的出口 IP**。

**好消息是你想要的「9 条通道同一个国家」完全可行**，而且比凑 9 个国家稳得多：

| 国家 | 当天节点数 | 够 9 条通道吗 |
|------|-----------|--------------|
| Japan | 42 | ✅ 够，还余 33 个备选 |
| Korea Republic of | 33 | ✅ 够，还余 24 个备选 |
| Thailand | 8 | ❌ 差 1 个 |
| United States | 5 | ❌ 差 4 个 |
| 越南 / 英国 | 2 | ❌ |
| 中国 / 缅甸 / 秘鲁 | 1 | ❌ |

所以 **Japan / Korea 两国都能轻松撑起 9 条通道的全独立出口**（实测日本分出了 9 个不同 IP：
`113.154.84.113 / 60.91.186.31 / 218.228.192.151 / 27.85.5.105 / 60.94.36.8 / 36.14.133.245 /
203.165.114.190 / 60.94.22.70 / 123.1.19.76`），每个 IP 还对应不同的宽带运营商。

反过来，越南、美国这些一天只有几个节点的国家，硬锁死"9 条全用它"是做不到的 —— 面板会提前告诉你而不是硬凑。

> 如果你要的是「9 条通道各自独立、但国家可以重复」，那最稳的选择就是：**全部 Japan** 或 **全部 Korea**；
> 如果你要的是「出口国家尽量多样」，那就用「尽量分到不同国家/地区」。

## 五、我实际验证过的内容

在本机起了一个真实实例（把数据目录改到临时目录）跑通：

1. 服务正常启动，9 个代理端口监听正常，拉取到 98 个节点并富化完成（新增 PTR 兜底生效，6 个 IP 走了反查）
2. 未登录 `POST /api/fetch_nodes`、`POST /api/channel/0/connect` → **401** ✓
3. 登录 → 带 cookie `POST toggle` → `{"ok": true, "enabled": false}` ✓
4. `POST /api/channel/99/toggle` → **400** ✓
5. `/api/nodes` 返回类型分布：住宅 78 / 机房 17 / 移动 3；`126.37.15.22` = 住宅，依据"命中宽带运营商(softbank)" ✓
6. 守护脚本对接真实面板：能正常登录、按各通道自己的国家发重连请求（CH0→Japan，CH3→Korea）、冷却生效、不崩 ✓
7. 原版 vs 新版守护脚本对比：原版在"CH0 被禁用"时抛出 `UnboundLocalError`，新版正常 ✓

**改账号/密码专项（46 项断言全过）**：

8. 明文 `ui_auth.json` 启动后自动变成 `pbkdf2_sha256$...`（日志有提示），admin/admin 仍能登录 ✓
9. 改账号+密码 → 200，返回 `请使用新账号密码重新登录`；**旧 cookie 立刻 401**，旧账号/旧密码都失效 ✓

## 六、怎么部署

`install.sh` 是用 `git reset --hard origin/main` 从仓库拉代码的，所以两种方式：

**方式 A（推荐，以后还能一键重装）**：把 `vpngate9_fixed/` 里的 6 个文件（`vpn_utils.py`、`vpngate9_multi.py`、`vpngate9_guard.py`、`proxy_server_multi.py`、`install.sh`、`README.md`）替换进你的 GitHub 仓库，commit + push，然后在 VPS 上执行：

```bash
bash <(curl -Ls https://raw.githubusercontent.com/Michaelwuzb/vpngate9/main/install.sh)
# 或直接： ml restart
```

**方式 B（不动仓库，直接覆盖）**：scp 上去再重启：

```bash
scp vpn_utils.py vpngate9_multi.py vpngate9_guard.py proxy_server_multi.py install.sh root@<VPS_IP>:/opt/michaelvpn/
ssh root@<VPS_IP> 'systemctl restart michaelvpn && systemctl restart vpngate9-guard 2>/dev/null; ml status'
```

> 注意：走方式 B 之后如果再执行 `install.sh`，会被 `git reset --hard` 覆盖回旧代码。

**升级后建议看一眼**：

1. 第一次启动会把旧缓存全部重判（一次性），面板"节点"列表里 IP类型 应该从大片"机房"变成大片"住宅"。
2. 启动日志应出现 `明文密码已升级为 PBKDF2 哈希存储` / `已生成守护令牌`。
3. **重启一次守护脚本**：`systemctl restart vpngate9-guard`（否则它还在按旧方式读明文密码）。
4. 登录后点右上角"管理员"，把 `admin/admin` 改掉（面板启动日志也会提醒）。

## 七、几个使用建议

1. **多出口直接点右上角「分配出口」**，别一条条手动选。想要出口国家尽量多样 → 选「尽量分到不同国家/地区」
   （当天凑不满会有提示）；想要 **9 条通道全走同一个国家但 IP 各不相同** → 选「全部通道用同一个国家/地区」，
   然后挑 `Japan` 或 `Korea Republic of`（这两国当天节点数 42 / 33，够摊开且还有大量备选）。
   现在即使 9 条通道全指日本也不会撞 IP（选节点即预占，掉线重连也会避开已占用的同国 IP）。
   一条经验：**IP 类型尽量留「不限」**。日本今天 42 个节点里住宅只有 27 个，锁死"住宅"会把池子砍掉三分之一；
   对多出口来说"能连上、IP 独立"比"住宅还是机房"更重要。手动指定时也别给多个通道选只有 1~2 个节点的国家
   （越南/缅甸/秘鲁这种），掉线就没备选了。
2. 想在面板上手动断掉某条通道且不让它自动重连：把那张卡片上的**"守护自动重连"勾掉**，然后点"断开"。勾回来之后需要手动点一次"连接"。
3. 判定关键词想加料：改 `vpn_utils.py` 顶部的 `RESIDENTIAL_ISP_KEYS` / `HOSTING_KEYS` / `MOBILE_KEYS`，然后把 `_CLS_VER` 加一即可（缓存自动失效）。
4. 面板仍在公网 `::` 监听 8787，建议顺手把它们放防火墙后面：`ufw allow from <你的IP> to any port 8787`，或者只监听 `127.0.0.1` 走 SSH 隧道。
5. 改成强密码后如果嫌每次登录麻烦，**别把面板暴露到公网**而是走 SSH 端口转发（`ssh -L 8787:127.0.0.1:8787 root@VPS`），然后访问 `http://127.0.0.1:8787`，比放公网安全得多。

## 九、新增：刷新出来的新节点做标记

### 之前是什么样
- `collector_loop()` 里写的是 `n["is_new"] = True` —— 每轮采集把**整池**都标成新节点，等于没标记
- `manual_fetch()` 虽然算了新增数，但基准只存在内存里，服务一重启就归零，第一次刷新又是"整池全新"
- 前端节点表**根本没渲染** `is_new` 字段，就算标了也看不见

### 现在怎么做的
- **首现时间持久化**：节点第一次出现的时间戳记进 `vpngate_data/nodes_seen.json`。
  判定"新"用的是**时间戳 + TTL**，而不是"本次刷新新增"这种一次性标记 ——
  采集间隔是 600 秒，一次性标记 10 分钟后就没了，用户根本来不及看
- **重启不刷屏**：启动时先 `load_seen_nodes()` 恢复基准，再启动采集线程
- **首次部署也不刷屏**：建立基准那一轮会把"新"的水位线一起抬到当前时刻
  （我们并不知道这批节点是什么时候上线的）。这是端到端测试里抓到的一个坑：
  首现时间等于"刚刚"时，`is_new_by_ttl` 会把整池都判成新节点
- **不会无限膨胀**：`_prune_seen()` 清理"既不在当前池里、首现又超过 `SEEN_KEEP_DAYS`(30天)"的记录
- **面板表现**：
  - 表格里新节点是绿色「新」徽标 + 浅绿底行，「发现时间」列显示"3 分钟前"这类相对时间
  - 筛选下拉增加 **只看新节点**、**已实测 / 未实测**
  - 顶部显示「节点: N · 新 M」
  - **清除新标记** 按钮：只挪水位线，首现历史不动，之后真新增的照样会亮
- **顺带修的问题**：手动 / 定时 / 启动 三条采集路径原来各写一套逻辑，
  现在统一到 `refresh_nodes_once()`，标记口径才不会一会儿全亮一会儿全灭

## 十、新增：测速

### 三个入口，测的东西完全不同

| 入口 | 测什么 | 怎么测 | 影响 |
|---|---|---|---|
| 节点表 **测延迟** | 节点 IP:端口 的 TCP 握手 RTT | 32 并发直连探测，**零流量** | 不碰任何通道 |
| 节点表 **测带宽** | 真实下载带宽 | 借一条**空闲通道**建隧道，经它的 SOCKS 口下载 | 占用 1 条空闲通道，15~30 秒/个 |
| 通道卡片 **测速** | 该通道当前出口的真实带宽 | 直接走这条通道自己的 SOCKS 口 | 只影响该通道，十几秒 |

### 为什么这么设计
- VPNGate 自带的 `Speed` 字段是节点上线时测的，参考价值有限，
  现在把它作为「官方速度」列并列展示，但不作为选择依据
- 延迟**必须从这台服务器实测**才有意义：官方 Ping 是从日本测的，跟你这台机器的实际体验差很远
- 带宽才是一切：所以「测带宽」是真拿隧道下载跑出来的数字

### 关键实现点
- **新增 `speedtest_utils.py`（纯标准库）**：自己实现 SOCKS5 握手（含用户名密码子协商）
  + HTTP/1.1 读取 + TLS，支持 `Content-Length` / `chunked` / 读到 EOF 三种响应形态
  - **chunk 头绝不能算进下载量**：1KB 小 chunk 时协议开销能占三成，带宽会虚高。
    这个 bug 是测试用例（B3b）抓出来的，现在用 `take(n, count=False)` 区分"净正文"和"协议开销"
  - 下载时丢弃前 `SPEEDTEST_WARMUP`(0.6s) 的字节（TCP 慢启动 + TLS 握手），只算稳定段吞吐
- **借通道测节点带宽**：只挑 `disconnected` 的空闲通道；借用时**临时把该通道的 `enabled` 置 False**，
  让外部守护进程（靠 `/api/status` 的 `enabled` 判断）在测速期间不来抢这条通道，测完自动还原。
  9 条全忙时明确拒绝并提示，**不会硬抢正在用的通道**
- **任务化 + 可中断**：延迟测试与带宽测速都是后台任务，前端 3 秒轮询进度条；
  带宽测速可随时 **停止**（当前节点测完就收工，不会留半截隧道）
- **结果不被冲掉**：`merge_node_metrics()` 在整池刷新时按 id 把上一轮的延迟/带宽合并回来
- **新增/变更接口**：
  - `POST /api/nodes/ping`（`?ids=` 可选，不传=全池）
  - `POST /api/nodes/speedtest`（`?ids=` / `?limit=`）、`POST /api/nodes/speedtest_stop`
  - `POST /api/channel/<i>/speedtest`、`POST /api/channels/speedtest`（已连接通道并发测）
  - `GET /api/nodes/speedtest` 取完整明细（含每个节点的失败原因）
  - `POST /api/nodes/clear_new` 清除新标记
  - `GET /api/nodes` 新增 `is_new / first_seen / new_age_s / tcp_latency / speed / test_out_mbps` 等字段，
    并支持 `filter=new|tested|untested` 与 `sort=new|latency|mbps|official`
  - `GET /api/status` 新增 `new_node_count / newest_node_at / ping_task / speed_task` 等
- **边界处理**：同类型任务不并行（409）；**测速中的通道不允许 connect/disconnect**（409，
  否则中途拆隧道会让结果变成 0，看起来像节点有问题）；对未连接的通道调测速会明确报错

## 十二、还没动的地方（你可以决定要不要）

- 面板仍是 HTTP 明文传输（密码本身已改为 PBKDF2 哈希存储）；需要的话可以加 HTTPS 自签证书或 Caddy 反代。
- `openvpn_cmd()` 里没显式设 `--tun-mtu`，靠节点配置自带值，目前实测没问题。
- `install.sh` 没有自动安装守护 service（README 是手动步骤），要的话我可以补成 `install.sh` 里自动装。
- 测速默认打 Cloudflare 的 `__down` 端点。如果你不想让面板主动往公网发 10MB 流量，
  可以调小 `SPEEDTEST_BYTES`，或把 `SPEEDTEST_URL` 指向自建测速服务器。
- 「测带宽」目前是**串行**的（一次借一条通道），9 条空闲通道时不会并行跑 9 个节点。
  想更快可以改成多通道并行，代价是会同时占用多条通道。
- 新节点标记只按"首次出现时间"判定，没有区分"这次出现的是不是上个月来过的老节点"。
  超过 `SEEN_KEEP_DAYS`(30天) 后会遗忘并重新算新 —— 这个行为我认为是合理的，但你要改成永久记忆也很容易。
